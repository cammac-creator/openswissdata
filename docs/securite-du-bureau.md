# Scripts du bureau privé

Le fichier construit `web/dist/admin/index.html` reçoit une politique spécifique, quelle que soit l’adresse qui a permis au serveur statique de le trouver. Le callback `onFound` marque le fichier effectivement servi ; le durcissement s’applique après le retour de `secureHeaders`. Les alias propres, avec barre finale, `index.html` et caractères encodés sont testés, ainsi que HEAD, OPTIONS, les réponses partielles et les requêtes simultanées.

La politique du bureau exige `script-src 'self'`, `script-src-elem 'self'` et `script-src-attr 'none'`. Aucun script inline, évaluation dynamique ni script tiers n’est ainsi autorisé. Les objets intégrés et les balises base sont interdits. Le HTML reçoit `private, no-store`. Une politique générale absente ou multiple interrompt la réponse au lieu de servir un bureau moins protégé. Les images sont limitées à la même origine et aux données intégrées ; les connexions et formulaires restent sur la même origine. La protection contre l’encadrement et les styles restent conservés. Cette mesure complète l’authentification, les contrôles d’origine et l’échappement du contenu ; elle ne prouve pas l’absence de toute faille XSS. Les scripts de même origine restent autorisés.

Le contrôle `npm run admin:csp:check`, obligatoire après le build, analyse le HTML du bureau et exige au moins un module local portant un nom compatible avec les empreintes Astro, dont le fichier existe. Il refuse les scripts inline, gestionnaires d’événement HTML, URL javascript, documents srcdoc et ressources liées par lien symbolique. Il refuse aussi une sous-page HTML supplémentaire sous admin, un lien dur sur la page principale, tout lien symbolique dans le site construit et toute autre page HTML citant le chemin du module du bureau. Son entrée CLI séparée s’exécute aussi lorsque le dépôt est atteint par un lien symbolique. C’est un contrôle de l’artefact produit par le projet, pas un assainisseur de HTML arbitraire. Il utilise explicitement la version de htmlparser2 déjà présente dans le lockfile ; aucun parseur n’est ajouté aux réponses du serveur ou au navigateur.

Le paramètre de construction `createApp({webRoot})` permet les essais dans un dossier temporaire sans modifier un build existant. Il n’est exposé par aucune route et ne lance pas les workers. Le service conserve son dossier par défaut `./web/dist`.

## Limites et retour arrière

Les pages publiques et l’espace compte possèdent encore des scripts inline, notamment des textes multilingues injectés au build. Ils demandent une migration distincte ; le retrait du bureau ne leur attribue pas une protection qu’ils n’ont pas. Les styles inline du bureau restent permis. Aucun nouvel endpoint de collecte de violations CSP n’est ajouté, afin de ne pas recueillir accidentellement des URL ou fragments privés.

Une évolution du bureau doit conserver ses scripts dans les fichiers produits par Astro et passer les essais navigateur. Si un script cesse de fonctionner, identifier sa source ; ne pas rétablir globalement unsafe-inline pour contourner un échec. Un retour à un code antérieur retire cette défense supplémentaire, sans modifier les données : sa portée doit être indiquée dans la passation.

Références consultées le 26.09.2026 : [ordre et configuration des en-têtes Hono](https://hono.dev/docs/middleware/builtin/secure-headers), [directive script-src et scripts inline](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src). Ordre réel et callback statique également relus dans les dépendances installées du projet.
